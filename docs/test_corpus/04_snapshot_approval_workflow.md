# Snapshot / Approval Workflow — the golden-master standard

> The project standard for **oracle (golden-master) discipline**. Driver:
> bead `padetaylor-krgy.9` (epic `padetaylor-krgy`, Tier §2.6 of
> `03_hardening_methodology.md:148-152`). This is the runbook a future
> contributor follows when adding, regenerating, or reviewing a pinned
> oracle value. It is **enforced**, not aspirational: the executable
> companion `test/oracle_provenance_test.jl` turns the suite RED when an
> oracle file violates the provenance contract below.

The corpus is anchored by ~25 `test/_oracle*.jl` files — flat lists of
pinned literals (closed-form values, mpmath / Mathematica / sympy captures,
exact rationals) that the `_test.jl` bodies assert against. As goldens
multiply, ad-hoc literals rot: a number whose origin nobody recorded cannot
certify anything (Rule 5), and a number nobody can re-derive cannot be
audited when it changes. This workflow closes both gaps.

## 1. The provenance contract (what every golden must declare)

Every oracle data file (`test/_oracle*.jl`) carries a **leading comment
header** — the contiguous `#`-block at the top, before the first line of
code — that declares, with non-empty content:

1. **SOURCE** — the ground-truth class the literals were derived from. One
   of: closed-form · exact rational/algebraic · mpmath · Mathematica /
   wolfram / NDSolve · sympy · scipy · TaylorIntegration · DMSUITE ·
   `padeapprox.m` · Calgo / FORTRAN · DLMF · binomial. State it explicitly
   (e.g. `mpmath 1.3, dps=50`, `closed-form p = z − z³/15`, `exact rational
   Padé(7,7) of exp`).
2. **REGENERATION / DERIVATION reference** — how to re-derive the value. A
   capture-script path (`external/probes/.../capture.{py,wl,m,jl}`,
   `verify.jl`) plus the one-line command to re-run it, OR — for an exact
   closed form — the derivation and a regenerate one-liner (e.g. the
   `fractions.Fraction` snippet in the catalogue record).
3. **TOLERANCE policy** — see §2. Encoded at the *assertion* site (in the
   `_test.jl` `@test ... atol/rtol`), restated in the header when the
   tolerance is load-bearing or non-obvious.

The well-formed corpus files already do this (most carry a rich
`REGENERATION ORACLE:` / `Generated by:` / `PROVENANCE` paragraph). The
provenance test encodes exactly the SOURCE + REGENERATION markers above and
asserts each header is non-trivial (≥ 3 comment lines, ≥ 80 chars of prose)
— a buried token does not satisfy the contract.

## 2. Tolerance: never bit-exact for derived floats

The single most important rule. **Choose the comparison kind by the value's
provenance, not by convenience:**

| Value kind | Comparison | Why |
|---|---|---|
| Exact **rational / integer / closed-form integer** (e.g. `a[1]=1/2`, `c_n=1`, residue ±1) | bit-exact `==` | the value is representable exactly; any drift is a real bug |
| **Derived float** — anything from SVD / Padé root-finding / a stepper / mpmath rounded to Float64 | `≈` with explicit `atol`/`rtol` | the last bits are platform-dependent (LAPACK/BLAS, arch); bit-exact would be a brittle false-RED |
| **High-precision string** parsed to Float64/BigFloat | parse the same string both sides, then `≈` at the precision floor | keeps the IC identical on both sides; see `_oracle_corpus_taylor_jet.jl` |

The package's numerical tier is bit-identical **only given** the platform
fingerprint `{arch, os, runtime}` (`src/PadeTaylor.jl` "Determinism"
docstring). A reviewer regenerating on another machine should expect
last-digit movement, **not** order-of-magnitude change. If a value moves by
orders of magnitude, that is a real regression — investigate it (Rule 2),
do not widen the tolerance to make it pass (Rule: "don't relax test
tolerances to make tests pass").

For *drift* tracking (a value that stays within its absolute-tol pin but
slowly loses digits), the accuracy ledger (§2.5 / `accuracy_ledger_test.jl`)
is the finer instrument; the per-value pin is the coarse correctness gate.

## 3. The regenerate → review → approve flow

Oracle updates are **explicit, reviewed commits — never silent**. Three
shapes, same discipline:

### 3a. Capture-script oracles (mpmath / Mathematica / sympy / Octave)
The header names the probe. Re-run it, then re-pin:

```sh
cd external/probes/corpus-oracles/<family>      # or external/probes/<name>-oracle
python3 capture.py                              # or: octave capture.m · wolframscript -file capture.wl
# verify.jl-backed probes additionally cross-check sources BEFORE writing:
julia --project=. verify.jl                      # asserts cross-oracle agreement, then writes the literals
```

Copy the labelled output into the `_oracle*.jl` file (or let `verify.jl`
write it), then **review the `git diff`** — every changed digit is visible —
and commit it as the new approved baseline.

### 3b. Env-var regeneration (the worked example — `accuracy_ledger_test.jl`)
The accuracy ledger demonstrates the gold-standard *in-suite* regeneration:
the test itself rewrites its baseline on demand, preserving the literate
header, and **never** writes on a normal run.

```sh
julia --project=. -e 'ENV["PADETAYLOR_REGEN_ACCURACY_BASELINE"]="1"; \
    include("test/accuracy_ledger_test.jl")'
```

This rewrites `test/accuracy_baseline.toml` from the current achieved
errors; the human then reviews the `git diff` (each `relerr` digit visible)
and commits. Both a genuine documented regression and a post-improvement
*tightening* go through this same review gate. New env-var-regenerable
goldens should copy this mechanism (guarded write, header preserved,
no-op on a normal run).

### 3c. Closed-form / hand-pinned values
Re-run the derivation one-liner cited in the header (or the catalogue
record), diff, approve. Exact rationals are pinned **inline in the test**,
not in the oracle file (only transcendental / derived pins live in
`_oracle*.jl`).

## 4. Snapshot vs hand-pinned value — when to use which

- **Hand-pinned literal** (the default here): a small, named set of
  representative values, each carrying its own provenance + tolerance. Use
  for scalar/short-vector goldens — the diff is human-readable and every
  number is individually justified. This is what the whole corpus does.
- **Snapshot** (whole-array / whole-image compared to a stored reference):
  use only when the artifact is large and structurally uninteresting to pin
  by hand (a full coefficient matrix, a rendered figure). Snapshots trade
  per-value justification for coverage — only adopt one when a hand-pin
  would be unreadable, and still record SOURCE + REGENERATION in the header.
  See §6 on ReferenceTests.jl (deferred).

## 5. Approval review checklist

Before committing a new or regenerated oracle, the reviewer confirms:

- [ ] **SOURCE** stated and independent of the routine under test (Rule 5 —
      not a self-pin; an mpmath/closed-form/exact value, not the package's
      own output re-frozen).
- [ ] **REGENERATION** reference present and *actually re-runs* (the cited
      `capture.*` / `verify.jl` / one-liner exists and reproduces the diff).
- [ ] **TOLERANCE** matches provenance: bit-exact only for rational/integer/
      closed-form-integer; `≈` with explicit `atol`/`rtol` for derived
      floats (§2).
- [ ] **Diff reviewed digit-by-digit**: last-digit movement is expected
      cross-platform jitter; order-of-magnitude movement is a regression to
      investigate, not to absorb.
- [ ] **`test/oracle_provenance_test.jl` is GREEN** (the header satisfies
      the contract).
- [ ] Commit message cites the probe path / catalogue record / ADR
      (Law 1).

## 6. ReferenceTests.jl — assessment (DEFER with condition)

`ReferenceTests.jl` provides `@test_reference` for array/image snapshot
testing (stores a reference artifact, diffs against it, with an interactive
approve-on-update flow). **Decision: DEFER** (Rule 9 — conscious defer,
not silent omission). Rationale:

- It adds a test-target dependency for a workflow the corpus does **not**
  currently need: every oracle today is a hand-pinned scalar/short-vector
  with individual provenance, which is *more* auditable than an opaque
  snapshot, not less.
- The figure tests (`ffw_fig_*`, `noumi_yamada_a4_figure`, …) assert
  numeric invariants, not pixel-rendered images, so image-snapshotting buys
  nothing here.
- Its approve-on-update UX would partly duplicate the env-var regeneration
  pattern (§3b) we already own dependency-free.

**Condition that would force adoption:** if a future oracle is a *large
derived array* (e.g. a full Padé coefficient matrix or a pole-field grid)
where hand-pinning every entry is unreadable AND a closed-form per-entry
check is unavailable — then `@test_reference` with a numeric tolerance
becomes worth the dep. Until then, hand-pinned literals + this workflow are
the standard. File a bead with that exact trigger if it arises.
